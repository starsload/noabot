# nanobot Windows 控制能力设计方案（2026-04-04）

## 设计目标
- 不把能力建立在“目标产品必须提供 API”这个前提上。
- 有 API 时优先使用 API；没有 API 时自动降级到可用手段。
- 默认优先稳定、可验证、可审计的控制方式，最后才使用鼠标键盘模拟。
- 让“视觉观察 -> 模型理解 -> 动作执行 -> 结果验证”成为一条正式能力链，而不是临时拼接。

## 总体原则
- 能不用坐标，就不用坐标。
- 能不用输入模拟，就不用输入模拟。
- 能先观察状态，就不要盲目执行动作。
- 每一步执行后都必须验证结果，而不是假设成功。
- 所有视觉信息都要先经过“适合模型”的预处理，再进入大模型。

## 分层执行模型

### 1. 系统接口层
适用场景：
- 文件操作
- 进程、服务、计划任务
- 注册表、系统设置
- PowerShell / WMI / CIM 可覆盖的系统管理任务

特点：
- 最稳定
- 最容易做权限控制和审计
- 不依赖 GUI 布局

### 2. 应用连接器层
适用场景：
- 浏览器 DevTools / Playwright
- Office COM
- 已知应用的本地 CLI、MCP、SDK、官方 API

特点：
- 成本低、成功率高
- 依赖外部能力，但不应成为整体方案前提

### 3. Windows UI Automation 层
适用场景：
- 标准桌面应用
- 可暴露控件树的 Win32 / WPF / 部分 Electron 应用

特点：
- 比截图找图和坐标点击稳定
- 可基于控件树做按钮、菜单、输入框定位

### 4. 视觉观察层
适用场景：
- 拿不到 API / CLI
- 拿不到稳定的 UI Automation 控件树
- 界面是图像化或自绘控件
- 需要让模型理解当前屏幕状态

能力：
- 全屏或局部截图
- OCR
- 模板匹配
- 图标/文本区域识别
- 将截图与上下文一并交给视觉模型做场景理解

特点：
- 不直接负责“做动作”，而是先负责“看见并解释当前状态”
- 是观察器，不是执行器

### 5. 输入事件兜底层
适用场景：
- 无法通过前四层完成操作时

能力：
- 鼠标移动、点击、拖拽
- 键盘输入、热键

特点：
- 最脆弱
- 风险最高
- 应作为最后兜底而不是主路径

## 推荐执行顺序
1. 先探测目标是否有系统接口或应用连接器。
2. 没有则尝试 UI Automation。
3. UIA 不可用则尝试视觉观察与视觉定位。
4. 最后才允许输入事件模拟。

## 核心执行闭环
每一步遵循：
1. 观察当前状态
2. 选择最优执行方式
3. 执行最小动作
4. 验证动作结果
5. 若失败则切换下一层能力，而不是继续盲点

## 动作抽象建议
建议让 planner 输出声明式动作，而不是底层坐标操作：
- `launch_app`
- `focus_window`
- `find_control`
- `click_control`
- `set_text`
- `invoke_menu`
- `run_command`
- `capture_region`
- `read_screen_text`
- `describe_screen`
- `wait_for_condition`
- `verify_condition`

再由 resolver 根据当前环境选择执行层。

## 对“不完整信息”的处理
系统不应依赖“用户提前告诉我们目标产品是否有 API”。

应把信息分为三类：

### 必须由运行时探测的信息
- 当前桌面有哪些窗口
- 当前有哪些进程
- 某窗口是否激活
- 某控件是否存在 / 可点击
- 某目标文件是否生成

### 可发现但非前置的信息
- 某软件是否有 UIA 控件树
- 某软件是否暴露 CLI / MCP / 本地协议
- 某窗口的标题、类名、进程名

### 可选增强信息
- 某产品官方 API
- 某业务系统专用适配器
- 某应用的模板图、已知选择器、业务规则

结论：
- API 是高质量增强通道，但不应成为前提。
- 真正的核心能力应是运行时探测、分层执行、自动降级与结果验证。

## 视觉观察链路设计

### 为什么要单独设计视觉链路
如果 nanobot 需要控制桌面应用，仅靠 OCR 或模板匹配还不够，因为很多任务首先要回答：
- 当前屏幕上是什么？
- 焦点在哪个窗口？
- 有没有报错弹窗？
- 某一步是否已经成功？

这些问题更适合由“截图 + 模型理解”来回答。

因此，视觉链路应当成为正式架构的一部分：
- 先截图
- 再做预处理
- 再传给视觉模型
- 再把模型结果转成结构化观察结论
- 最后驱动后续动作

### 视觉链路的标准流程
1. 截取当前屏幕或局部区域
2. 对图片做规范化
3. 生成适合模型消费的图像消息
4. 让视觉模型输出场景描述或结构化观察
5. 将观察结果交给 planner / verifier

### 图片进入模型前的规范化要求
这次改造已经验证，桌面截图如果原样内联为 data URI，容易因为尺寸或字节过大触发模型侧限制。

因此视觉链路必须内建图片预处理：
- 限制最大边长
- 限制 inline 图片字节预算
- 必要时自动缩放
- 必要时自动转 JPEG
- 尽量保留可读性，而不是追求原图无损

对应设计要求：
- 所有进入模型的 inline image 必须统一走同一套 helper
- 无论图片来自用户上传，还是来自 `read_file()` 读取截图，都不能绕过这套处理
- 若模型返回图片尺寸/载荷限制错误，应优先尝试“规范化后重试”，而不是直接丢图

### 视觉观察器的输出建议
视觉模型的输出不应只是一段自由文本，建议逐步收敛为结构化结论，例如：
- `active_window_guess`
- `visible_buttons`
- `detected_error_banner`
- `ocr_hits`
- `game_state`
- `dialog_present`
- `recommended_next_target`

第一阶段可以先允许自由文本描述。
第二阶段建议加上结构化 schema，便于 planner 和 verifier 消费。

## “视觉观察 -> 执行”协作模型

### 观察器负责什么
- 读取截图
- 向视觉模型请求解释
- 输出当前场景结论

### 执行器负责什么
- 根据场景结论选择动作
- 优先使用系统接口 / UIA / 连接器
- 只有在没有更好路径时才做鼠标键盘模拟

### 验证器负责什么
- 执行动作后再次观察
- 判断界面是否变成预期状态
- 若未达成目标，反馈给 planner 做下一轮决策

## 推荐的桌面任务闭环
以“打开应用并点击导出”为例：
1. 检查进程和窗口是否存在
2. 若未启动则通过系统层启动应用
3. 启动后优先尝试 UIA 找“导出”按钮
4. 若 UIA 不可用，则截图并让视觉模型判断“导出”按钮位置或界面状态
5. 需要时结合 OCR / 模板匹配进一步定位
6. 最后才执行点击动作
7. 点击后再次截图并验证文件是否生成 / 状态是否变化

## 安全控制建议
- 默认 `dry_run=true`
- 高风险动作要求显式确认
- 默认禁止在未知窗口执行连续文本输入
- 默认禁止支付、密码、管理员弹窗中的自动输入
- 焦点窗口漂移后自动中止
- 每步写 action log
- 提供紧急停止
- 提供仅观察模式

## 第一阶段建议落地范围
- 系统层：PowerShell、进程/窗口探测、文件验证
- 浏览器层：DevTools / Playwright
- 桌面层：UI Automation 的窗口、按钮、输入框、菜单操作
- 视觉层：
  - 截图
  - OCR
  - 模板匹配
  - 截图经预处理后传给视觉模型做场景理解
- 兜底层：受严格安全策略约束的鼠标键盘模拟

## 第二阶段建议落地范围
- 为视觉模型输出增加结构化 schema
- 把“观察结论”与执行器接口打通
- 引入局部截图、区域复查、差异截图
- 引入针对窗口标题、应用类型、场景的专用观察 prompt 模板
- 对视觉失败原因做分类：
  - 图像过大
  - 图像不清晰
  - OCR 无命中
  - 模型未识别关键元素

## 与本次图像链路改造的关系
本次图像识别链路修复说明：
- nanobot 已经具备“截图 -> 预处理 -> 传模识图”的基础链路
- 后续 Windows 控制能力设计应直接建立在这条链路之上
- 不应再把截图识图视为临时技巧，而应视为正式观察通道

配套验证报告：
- `case/reports/2026-04-04-image-vision-fix-report.md`

## 一句话结论
更合理的目标不是“让 nanobot 模拟人类操作 Windows”，而是“让 nanobot 通过分层控制通道和正式的视觉观察链路来理解并操作 Windows 应用，在能力不足时安全降级”。
